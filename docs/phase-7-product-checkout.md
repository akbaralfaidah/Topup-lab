# Phase 7 transaction preparation and quote preview

Phase 7 turns `/games/[slug]` from a denomination preview into a transaction-preparation page. Non-game products use `/products/[slug]`; both routes share `PreparationForm`. The four visible sections are Data akun, Pilih nominal, Pembayaran, and Konfirmasi. The last action, “Pratinjau pesanan,” produces a review panel only. No order, payment, price snapshot, wallet entry, provider attempt, or transaction reference is created.

## Data and server boundary

The server loads active products with their versioned `ProductInputSchema` definition and validates that definition against the Phase 3 strict Zod schema. Game denominations must share the same definition. The client renders labels, format hints, and length limits from that public schema; it does not hard-code a form per game. `validateTarget` normalizes whitespace in text, removes spacing in numeric identifiers, and accepts an Indonesian `08…` phone input as `+628…`. It checks required values, lengths, formats, unexpected fields, and control characters. The browser uses it on blur and before review, while the quote endpoint independently validates submitted target values. Target data stays in short-lived component state and a single request body. The endpoint returns only masked trailing characters for review. It does not persist or log plaintext identifiers, and it never requests a password, OTP, cookie, or token.

`POST /api/demo/quote` is a narrowly scoped, read-only calculation. It accepts only a product slug, one of three demo payment codes, and optional target fields. Input size, JSON shape, origin, active product, and product availability are checked. A quote request re-reads eligibility rather than trusting the catalog card or browser price. Errors expose stable customer-safe states without SQL, provider, or rule details. The route is no-store and is disabled in production/live mode by the established local-demo guard. There is no account verification or publisher/provider connectivity. Cross-site callers cannot use it to read a response, and an Origin header from another origin is rejected; shared rate limiting remains future infrastructure work.

## Deterministic quote calculation

`readDemoPreviews` selects only eligible demo provider mappings: enabled mapping, available flag, enabled provider in HEALTHY or DEGRADED state, and stock not OUT_OF_STOCK. It chooses the lowest configured priority, then lowest cost, then stable mapping ID. This candidate is for preview only; future fulfillment routing remains authoritative. The candidate and its cost never appear in the public DTO or HTML.

The default unauthenticated tier is Public. No client tier selector or inferred membership exists. Active, scheduled rules are resolved at the fixed Phase 4 demo reference instant, 24 September 2026 at 12:00 WIB. Scope precedence is **product > brand > category > global**. Within a scope, an exact Public-tier rule wins over a tier-neutral rule; lower numeric priority wins next, then stable rule ID. Provider-scoped rules are deferred to the Phase 8 pricing policy and are not applied to these demo previews. Missing or invalid pricing configuration fails closed.

All monetary arithmetic uses bigint IDR. Percentage markup is `ceil(cost × markupBps / 10_000)`, computed as integer division `(cost × bps + 9_999) / 10_000`. Markup is fixed markup plus that percentage. Product price is `cost + max(markup, minimumMargin)`. The service rejects negative values, noninteger or out-of-range basis points, and totals above PostgreSQL bigint's maximum. Zero and large values above JavaScript's safe integer range are covered by tests. Monetary DTO fields are decimal strings; presentation inserts Indonesian grouping separators without converting to Number.

The explicit local demo payment fees are QRIS Rp0, Virtual Account Rp2.500, and E-Wallet Rp1.500. They are calculated on the server and described as examples, never as gateway terms. The breakdown shows product price, fee, and total. Promo discounts and flash-sale pricing are omitted because no eligibility/redemption engine is active and Phase 4 promotions are tied to a fixed reference time. Phase 11 payment integration must replace the fee configuration. These previews are mutable calculations; commercial terms become immutable only when a later order writes a validated `PriceSnapshot`.

## Presentation and limits

The initial denomination prices render in server HTML. The client island handles temporary target fields and selections, requests a fresh quote when denomination or payment changes, and requests it again with validated target data for review. Stale selection requests are aborted. The final review masks target values and states explicitly that checkout is not active. Disabled denominations cannot be chosen. A desktop summary stays visible beside the form; tablet and mobile layouts use the existing SmartCheckoutBar with reserved bottom space and hide it while a target field has focus to avoid keyboard obstruction. Reduced motion makes the review transition immediate.

There is no membership preview, promo entry, flash reservation, account verification, payment QR/VA number, success page, or order record. Production and live modes remain unavailable. The 12-product, 100-candidate, and 200-rule query ceilings fail closed; a larger catalog requires a more focused pricing query. Phase 8 administration, Phase 10 order creation, and Phase 11+ payment/provider operations remain separate work.
