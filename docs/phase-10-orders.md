# Phase 10: Persistent Order Creation

This phase implements the authoritative, persistent commerce transaction foundation. A customer or guest checkout request now becomes an immutable `Order` with a corresponding `PriceSnapshot` and an initial entry in `OrderStatusHistory`.

## Order Creation Architecture

The system employs a strict backend order creation boundary located at `/api/checkout/submit`.
It performs the following:

1. Validates the `quoteToken` ensuring quote binding and unexpired session limits (15 minutes).
2. Validates CSRF/Origin boundaries.
3. Retrieves the authoritative `product`, `inputSchema`, and executes validation on the provided target.
4. Reprices the product dynamically using the Phase 8 engine, rejecting the request explicitly if the calculated total doesn't match the quote (`PRICE_CHANGED`).
5. Performs AES-256-GCM authenticated encryption on target details.
6. Submits the persistent mutation through a PostgreSQL atomic transaction inserting `price_snapshots`, `orders`, `order_items`, and `order_status_history`.

## Quote Binding

To avoid trusting client-provided prices, a `quoteToken` (HMAC-SHA-256) is issued upon previewing an order. The token binds `productSlug`, `paymentMethod`, and `totalIdr` to an expiry limit (15 mins). On checkout, the server re-calculates the price from scratch. If the token is valid but the recalculated price deviates from `totalIdr`, the server issues a safe `PRICE_CHANGED` error forcing the user to review the updated price.

## PriceSnapshot

A `PriceSnapshot` encapsulates the complete commercial terms at the moment of checkout (provider cost, tier, markup, and final price). This record is strictly immutable and shields the order history from any subsequent changes in the `pricing_rules` or `provider_skus` structure.

## Idempotency

Submissions require an `idempotencyKey` randomly generated by the client upon checkout intent. The server validates idempotent replays strictly:

1. **Idempotency Ownership:** Replays are rejected (`order_conflict`) if the session/guest identity does not exactly match the original request.
2. **Logical Equivalence:** Replays are rejected (`order_conflict`) if the request payload (product, total amount, or target) deviates from the original record.
   If both checks pass, the server transparently returns the original `publicReference`. The database uniqueness constraint on `orders.idempotencyKey` serves as the ultimate concurrency backstop, guaranteeing exactly one logical transaction per key.

## State Machine

The domain manages a central finite state machine in `src/server/orders/state-machine.ts`. Order status mutations are governed by `validTransitions` rejecting arbitrary skips (e.g. `WAITING_PAYMENT -> SUCCESS` without processing). PostgreSQL `UPDATE` queries embed an optimistic conditional check `orders.status = fromStatus` to eliminate race conditions, alongside a strict history audit log.

## Target Encryption and Key Rotation

`order_items.targetCiphertext` uses AES-256-GCM. The plaintext target never touches disk in an unencrypted state.
The system implements a robust Key Ring architecture to support key rotation without rewriting historical data:

- **Key Ring Configuration:** The server requires `TARGET_ENCRYPTION_ACTIVE_KEY_ID` (the active key identifier) and `TARGET_ENCRYPTION_KEYS` (a JSON map of key IDs to 32-byte hexadecimal master keys).
- **Active Key:** New orders are always encrypted using the key corresponding to `TARGET_ENCRYPTION_ACTIVE_KEY_ID`.
- **Key ID Persistence:** The active key ID is persisted as `targetKeyReference` alongside the ciphertext.
- **Historical Keys:** The server utilizes the persisted `targetKeyReference` to look up the exact key used for decryption. This allows `TARGET_ENCRYPTION_ACTIVE_KEY_ID` to be rotated securely while older keys are kept in the keyring solely for decryption of historical orders.
- **Fail-Closed Behavior:** If a ciphertext references an unavailable key ID, the system fails closed with an internal exception. It does not attempt to guess keys, and it never exposes key references or missing key states to the customer UI.
- **Secret Separation:** `TARGET_ENCRYPTION_KEYS` is structurally separated from `QUOTE_HMAC_KEY` and `GUEST_HMAC_KEY`, guaranteeing cryptographic isolation between distinct bounded contexts.

## Guest Order Security

Guests lacking a session acquire a temporary HMAC-signed capability token (`topuplab_guest` HttpOnly cookie). This token is strictly scoped:

1. **Path-Scoped Execution:** The cookie uses a dynamic `Path=/orders/{publicReference}` to support multi-order cartless guests without cookie overwriting.
2. **Secret Separation:** The capability HMAC relies on a distinct secret (`GUEST_HMAC_KEY`), avoiding cross-purpose contamination with Quote bindings.
   This blocks IDOR scans by ensuring predictable UUID references cannot be loaded without cryptographic proof of ownership.

## Authenticated Order Ownership

Logged-in members (`userId`) have their identity mapped natively to `orders.customerId`. The application implicitly trusts the Phase 9 authenticated session above any client-side assertions, neutralizing parameter tampering.

## Phase 11 Boundary

No payment generation (QR/VA) or provider fulfillment adapters have been constructed in Phase 10. The checkout securely places the user at `WAITING_PAYMENT`.
