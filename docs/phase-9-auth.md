# Phase 9: Authentication and Authorization

This phase implements the production-oriented identity and authorization foundations for TOPUPLAB, conforming to strict security standards. The architecture deliberately eschews complex OAuth/OIDC libraries in favor of a tightly controlled, verifiable, database-backed session model that explicitly supports our `customer_profiles` and pricing authorization boundaries.

## Architecture and Mechanisms

### Password Authentication

Passwords are hashed using **Argon2id**. We enforce standard complexity and length checks during registration. The system natively handles secure authentication through a dedicated `password_credentials` table, avoiding storage of hashes directly in the `users` table to maintain a clean domain boundary.

### Session Management

Sessions are token-based. We issue random 32-byte opaque session tokens (bearers) to the client, stored in a secure, `HttpOnly`, `SameSite=Lax` cookie. The database (`sessions` table) only stores the SHA-256 digest of this token. This ensures that even if the database is fully compromised, active sessions cannot be stolen.

### Role-Based Access Control (RBAC)

The system uses a clean relational RBAC model (`roles`, `permissions`, `user_roles`, `role_permissions`).
The `rolePolicy` definition strictly limits permissions based on explicit roles:

- `CUSTOMER`: No administrative privileges.
- `RESELLER`: No administrative privileges.
- `ADMIN`: Has `admin.access`, `pricing.read`, and `pricing.write`.
- `SUPER_ADMIN`: Has identical capabilities to `ADMIN`, typically used for initial bootstrapping.

### Access Boundaries

1. **Public/Guest:** Browsing the catalog and basic checkout operations remain available to guests.
2. **Account (`/account`):** Requires an active session. Protected by `requireSession()`.
3. **Admin Shell (`/admin`):** Requires both an active session and the `admin.access` permission. Protected by `requireAdminAccess()`.
4. **Action Permissions:** Specific mutations (like `saveRule`) require explicit granular permissions (e.g. `pricing.write`), verified centrally within the API route.

## Administrative Bootstrapping

By design, TOPUPLAB ships with _no_ default administrative credentials. To bootstrap the first administrative user, an explicit, out-of-band CLI tool must be used:

```bash
# Sets the required confirmation flag and grants SUPER_ADMIN to an existing customer account
$env:AUTH_BOOTSTRAP_CONFIRM="GRANT_SUPER_ADMIN_TO_EXISTING_USER"
npx tsx scripts/bootstrap-admin.ts --email=admin@example.com
```

This action is immutably recorded in the `audit_logs` as an `EXPLICIT_OPERATOR_BOOTSTRAP`.

## Integration with Pricing

The Phase 8 demonstration pricing workspace (`/dev/admin/pricing`) has been promoted to a production-ready route (`/admin/pricing`).
The backend mutation endpoints (`/api/admin/pricing`) now enforce real role-based permission checks and attribute the actor's identity (`actorId`) in the audit logs when recording `PRICING_RULE_CREATE` or `PRICING_RULE_UPDATE` events.

## Security Guarantees

- **No Client-Side Authority:** Roles and permissions are strictly read and evaluated on the server.
- **CSRF Defense:** State-changing API routes implement strict `Origin` and `Host` header validations (`validMutationOrigin`).
- **No Secrets in Logs:** Authentication failures return generic error codes. Stack traces and unhandled exceptions do not leak context.

## Deferred Security Infrastructure

- **Rate Limiting**: Production-grade distributed rate limiting (e.g. via Redis 7.x) is not currently implemented on the authentication boundaries (login, registration). Deployments must provision and configure a robust rate limiter at the ingress or API gateway level to prevent brute-force and enumeration attacks before Phase 10 production release.
- **Content-Security-Policy (CSP)**: A strict CSP is deferred. While standard security headers (`X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`) are enforced via Next.js, a full CSP requires careful auditing of inline scripts/styles generated by Next.js/React. This remains a deployment requirement for hardening.
- **Email Verification & Password Recovery**: Simulated infrastructure has been strictly avoided. True email verification and password reset workflows remain deferred until a genuine transactional mail provider is integrated.
